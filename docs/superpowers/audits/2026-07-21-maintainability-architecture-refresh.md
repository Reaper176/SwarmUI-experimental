## Current Architecture

### Repository and composition baseline

#### Runtime layers

SwarmUI has three principal maintained runtime layers: a classic-script/Razor browser frontend under `src/Pages`, `src/wwwroot/js`, and `src/wwwroot/css`; the C# application and Web/API host under `src`; and Python execution supplied chiefly by excluded upstream Comfy code, with Swarm-owned nodes confined to `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes` (`AGENTS.md`, `src/Core/Program.cs`, and `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes`). Built-in extensions under `src/BuiltinExtensions` connect these layers without changing the executable composition root.

#### Process lifecycle

`Program.Main` is the process composition and lifecycle root (`src/Core/Program.cs`). After loading settings, it calls `Extensions.PrepExtensions`; that method discovers and instantiates extensions, then invokes `OnFirstInit` and `PopulateMetadata` through separate `RunOnAllExtensions` passes (`src/Core/ExtensionsManager.cs`). Back in `Program.Main`, the ordered phases continue with extension `OnPreInit`, model-list and default-parameter registration, construction of `BackendHandler`, `SessionHandler`, and `WebServer`, `Web.PreInit`, extension `OnInit`, model and backend loading, API registration through `BasicAPIFeatures.Register`, Web-host preparation, extension `OnPreLaunch`, and launch. `Program.Shutdown` invokes `PreShutdownEvent`, cancels `GlobalProgramCancel`, stops the Web host, backends, sessions, proxy, and model handlers, then calls extension `OnShutdown` and shuts down output metadata tracking. Process-wide owners remain publicly reachable through `Program.Backends`, `Sessions`, `T2IModelSets`, `Extensions`, `ServerSettings`, `Web`, and `GlobalProgramCancel`.

The exact-token maintained-C# consumer inventory, bounded to `src/**/*.cs` while excluding `src/Data`, external extensions, downloaded nodes, and build output, found: `Program.Backends` 64 occurrences in 18 files; `Program.Sessions` 58 in 8; `Program.T2IModelSets` 45 in 16; `Program.Extensions` 13 in 3; `Program.ServerSettings` 178 in 42; `Program.Web` 5 in 4; and `Program.GlobalProgramCancel` 91 in 25. These counts identify the breadth of the existing composition surface; they do not characterize those references as defective.

#### Web/API composition

`WebServer` owns ASP.NET/Razor composition and request routing (`src/Core/WebServer.cs`). `WebServer.Prep` configures middleware, response compression, static files, WebSockets, Razor Pages, shutdown integration, the `/API/{*Call}` dispatcher, output/view routes, extension files, and audio. `API.APIHandlers` is the route registry; `API.RegisterAPICall` adds either an `APICall` or a reflected delegate; and `API.HandleAsyncRequest` owns HTTP/WebSocket parsing, session resolution, permission enforcement, reflective dispatch, and response/error transport (`src/WebAPI/API.cs` and `src/WebAPI/APICallReflectBuilder.cs`). `BasicAPIFeatures.Register` registers account/session/general routes and composes `T2IAPI`, `ModelsAPI`, `BackendAPI`, `AdminAPI`, `UtilAPI`, and `PromptLabAPI` (`src/WebAPI/BasicAPIFeatures.cs`). Static registration searches found 147 `API.RegisterAPICall` sites across 11 maintained C# files, including built-in Comfy, Grid Generator, and Image Batch Tool contributions.

#### Current extracted boundaries

The current T2I route owner is already split by capability: `T2IAPI.Register` preserves the route-composition surface while registering methods owned by `ImageHistoryAPI`, `KritaAPI`, and `ClassicInpaintAPI` alongside generation and parameter/model-refresh methods (`src/WebAPI/T2IAPI.cs`, `src/WebAPI/ImageHistoryAPI.cs`, `src/WebAPI/KritaAPI.cs`, and `src/WebAPI/ClassicInpaintAPI.cs`). On the browser side, `ImageHistoryController` remains in `src/wwwroot/js/genpage/gentab/outputhistory.js` and composes `ImageHistoryFilter`, `ImageHistoryComparison`, and `ImageHistoryBulkActions` from `src/wwwroot/js/genpage/gentab/imagehistoryfilter.js`, `src/wwwroot/js/genpage/gentab/imagehistorycomparison.js`, and `src/wwwroot/js/genpage/gentab/imagehistorybulkactions.js`; the Image Editing coordinator is owned by `src/wwwroot/js/genpage/helpers/image_editor_ui.js`. These are current committed boundaries, not assumptions carried forward from the 2026-07-20 audit.

#### Extension composition

`ExtensionsManager` discovers built-in extension types from loaded assemblies and external extension projects from `src/Extensions` and instantiates `Extension` subclasses (`src/Core/ExtensionsManager.cs`). Its `RunOnAllExtensions` performs the per-phase iteration requested by callers; `Program` establishes the lifecycle phase order. The `Extension` base contributes `ScriptFiles`, `StyleSheetFiles`, `OtherAssets`, metadata, and `OnFirstInit`/`OnPreInit`/`OnInit`/`OnPreLaunch`/`OnShutdown` hooks (`src/Core/Extension.cs`). Extensions also contribute through shared registries such as `API.RegisterAPICall`, `T2IParamTypes.Register`, `BackendHandler.RegisterBackendType`, permissions, and `WorkflowGenerator` step lists. `WebServer.GatherExtensionPageAdditions` converts extension script/style/asset lists and `Tabs/Text2Image/*.html` files into served resources and generated page fragments. Thus `Program` owns lifecycle order, `ExtensionsManager` owns discovery, instances, and per-phase iteration, each `Extension` owns its contribution declarations, and `WebServer` materializes browser-facing contributions.

#### Backend/session/model state

Backend ownership is centered on `BackendHandler`: `AllBackends` is a concurrent configured-instance registry, `BackendTypes` is the type catalog, `Load` and `Shutdown` own configured lifecycle, and `GetNextT2IBackend` plus request/pressure registries coordinate T2I acquisition and model-loading pressure (`src/Backends/BackendHandler.cs`). `SessionHandler` owns concurrent session, user, and role registries plus persistent login sessions (`src/Accounts/SessionHandler.cs`). Each `T2IModelHandler` owns a concurrent model catalog and refresh/shutdown behavior, while `Program.T2IModelSets` maps model categories to those handlers (`src/Text2Image/T2IModelHandler.cs` and `src/Core/Program.cs`).

#### Comfy adapter

The Comfy built-in is the adapter boundary between C# generation and Python nodes. `src/BuiltinExtensions/ComfyUIBackend/ComfyUIBackendExtension.cs` registers assets, parameters, backend types, lifecycle work, and feature discovery; `src/BuiltinExtensions/ComfyUIBackend/ComfyCapabilityCatalog.cs` supplies selected detected-node-to-feature mappings. `src/BuiltinExtensions/ComfyUIBackend/ComfyNodeNames.cs` catalogs Swarm-maintained node class names, while `src/BuiltinExtensions/ComfyUIBackend/ComfyNodeInputNames.cs` catalogs approved schema-backed input keys used by built-in code. These are bounded compatibility catalogs, not inventories of every Comfy class name, input, or string. Their maintained consumers include `src/BuiltinExtensions/ComfyUIBackend/WorkflowGenerator.cs`, `src/BuiltinExtensions/ComfyUIBackend/WorkflowGeneratorSteps.cs`, `src/BuiltinExtensions/ComfyUIBackend/WorkflowGeneratorModelSupport.cs`, and `src/BuiltinExtensions/ComfyUIBackend/WGNodeData.cs`, which build Comfy JSON graphs and ordered generation steps. On the Python side, `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes/SwarmComfyCommon/__init__.py` composes common `NODE_CLASS_MAPPINGS`, `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes/SwarmComfyExtra/__init__.py` conditionally composes optional mappings, and node modules such as `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes/SwarmComfyCommon/SwarmSaveImageWS.py`, `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes/SwarmComfyCommon/SwarmKSampler.py`, and `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes/SwarmComfyExtra/SwarmSaveAnimationWS.py` define registration entries and `INPUT_TYPES` schemas. Downloaded Comfy and node repositories remain outside maintained scope.

#### Launch/install/update surfaces

The read-only launcher surface has distinct platform paths. `launch-linux.sh` and `launch-macos.sh` source `launchtools/linux-build-logic.sh`, which repairs the .NET path, optionally pulls, rebuilds when commit markers demand it, retains a failed-build backup, and sets host environment before the launcher starts the built server; exit code 42 re-enters the launcher. `launch-windows.bat` carries equivalent pull/build/backup/start/restart logic, while `launch-linux-dev.sh` and `launch-windows-dev.ps1` force debug rebuild paths. `launchtools/install-linux.sh` and `install-windows.bat` install prerequisites, clone SwarmUI, and hand off to the platform launcher. Docker launch scripts build the selected Dockerfile, mount the applicable repository/data/backend paths, and call inner scripts that return to `launch-linux.sh`. Separately, runtime installation and updates are owned by `Installation.Install` and Admin API routes such as `CheckForUpdates`, `UpdateAndRestart`, extension update/install methods, and `InstallDotnetUpdate` (`src/Core/Installation.cs` and `src/WebAPI/AdminAPI.cs`).

### Frontend, Razor, and Web composition

#### Layout and classic-script order

`src/Pages/Shared/_Layout.cshtml` is the browser composition root. In the head it emits, in order, the selected dark/light Bootstrap stylesheet, Select2 styles, `site.css`, the page `Header` section, extension styles through `WebServer.PageHeaderExtra`, and the selected theme styles. It then loads jQuery, Bootstrap, Select2, `util.js`, and `translator.js`. After the page body it loads `permissions.js`, then `site.js`, then the page `Scripts` section. Consequently generation-page code can rely on utility, translation, permission, request, and session globals, while theme CSS has later cascade position than core, page, and extension CSS. This ordering is a compatibility contract; the maintained CSS searches found responsive rules, fixed-position overlays, z-index layers, and `!important` overrides, but those constructs are contextual evidence of the existing cross-theme/browser contract rather than findings.

`src/Pages/Text2Image.cshtml` supplies the generation-page order inside that `Scripts` section. After the excluded EXIF dependency, the base sequence is `welcomemessages.js`, `browsers.js`, presets, wildcards, base `loras.js`, models, params, prompt tools, utility/user-tab definitions, `generatehandler.js`, Simple tab, layout, metadata, generation controls, current-image handling, the three image-history collaborators, `outputhistory.js`, notes, base `main.js`, Prompt Lab, settings editor, UI improvements, and media controls. `WebServer.PageFooterExtra` then appends extension scripts; `finalscript.js` is last and schedules `genpageLoad` with a one-millisecond timeout. Static source establishes declaration and scheduling order, not when a particular browser will execute the queued timer relative to unrelated work.

`Extension.ScriptFiles`, `StyleSheetFiles`, and `OtherAssets` are public contribution lists populated by extensions (`src/Core/Extension.cs`). `WebServer.GatherExtensionPageAdditions` iterates `Program.Extensions.RunOnAllExtensions`: scripts and styles become cache-varied `ExtensionFile/{ExtensionName}/...` tags, other assets become served binary entries, and `Tabs/Text2Image/*.html` files become permission-gated top-tab header/body fragments. It assigns the resulting strings to `PageFooterExtra`, `PageHeaderExtra`, `T2ITabHeader`, and `T2ITabBody` (`src/Core/WebServer.cs`). Text2Image places extension tab headers between Image Editing and Utilities, extension bodies after the Image Editing shell, and extension scripts immediately before `finalscript.js`. Extension order, classic-script globals, tab IDs, and the final-script position must therefore remain compatible even though external extensions are outside the auditable consumer inventory.

#### Generation-page initialization, session callbacks, and lazy tabs

`genpageLoad` in base `src/wwwroot/js/genpage/main.js` first binds Bootstrap top-tab handlers, initializes `genTabLayout`, starts a status request, and starts hash restoration. It then calls `getSession` from `site.js`. A successful `GetNewSession` sets `session_id`, `user_id`, output-prefix behavior, permissions, and server-version state before invoking the callback. The generation callback builds the history shell, requests `ListT2IParams`, loads model classes/models/wildcards and parameter definitions, applies parameter configuration, creates inputs/tools, restores UI state, and runs `sessionReadyCallbacks` in insertion order. Core scripts register the server-lazy-tab callback in `main.js`, Prompt Lab initialization in `promptlab.js`, and settings-editor initialization in `settings_editor.js`; PageFooter extension scripts then register maintained Comfy workflow preparation, Grid Generator registration, and Image Batch Tool registration in extension iteration order. Excluded external extension scripts may also use the global array. The successful tail starts the Krita poll, welcome/title work, marks `swarmHasLoaded`, and schedules initial history loading. A `ListT2IParams` failure warns and still schedules history, but does not run the successful tail. There is no maintained `postSessionReadyCallbacks` definition or consumer at the pinned base.

`genericRequest` and `makeWSRequest` both attach the current session and reacquire one after an `invalid_session_id`; these request-level retries do not rerun the one-time `sessionReadyCallbacks`. `getSession` throttles checks within one second and reports a server-version change. Separately, status polling suppresses hidden-page requests until at least thirty seconds have elapsed since the last hidden-page poll; after a response, a non-empty status class selects a two-second interval and an empty class selects sixty seconds, independently of document visibility. Static source supports this reconnect/request behavior; it does not establish runtime network timing.

Text2Image's `lazyTabs` list emits placeholder panes and `window.genpageLazyTabs`; `window.genpageLazyScriptGroups` gives Image Editing the ordered `color_picker.js`, `image_editor_tools.js`, `image_editor.js`, and `image_editor_ui.js` group and gives Server its ordered backend/server/log scripts. In `main.js`, `loadScript` memoizes by exact `src`, creates non-async script elements, and rejects with the source path; `ensureLazyScriptGroup` awaits each source in manifest order. `ensureLazyTabMarkup` then calls permission-gated `GetGenPageTabPartial`, replaces the shell with returned HTML, enables sliders, and applies translations. `activateLazyTab` performs scripts, markup, and the tab hook exactly once per successful activation; failures clear activation/loading state for retry. Bootstrap `show.bs.tab` assigns a monotonically increasing request ID, `shown.bs.tab` activates the lazy tab, and stale request IDs prevent later sub-tab/hash work from an older open request. `UtilAPI.LazyGenPageTabPartials` is the server allowlist and permission check for the same four keys (`src/WebAPI/UtilAPI.cs`).

## Primary Cross-Layer Flows

### Browser boot, session establishment, and lazy tabs

1. `_Layout.cshtml` resolves the theme and emits base/page/extension/theme CSS, then jQuery/Bootstrap/Select2, `util.js`, and `translator.js`. After the Razor body it emits `permissions.js`, `site.js`, and Text2Image's ordered script section.
2. `Text2Image.cshtml` emits server-derived feature toggles, Comfy installable-feature data, parameter remaps, lazy-tab descriptors/script groups, eager Generate/Simple/optional Prompt Lab markup, lazy shells, and extension tabs. Its scripts define shared browser helpers and feature owners; extension scripts follow the maintained scripts; `finalscript.js` queues `genpageLoad` last.
3. `genpageLoad` binds Bootstrap/hash/lazy-tab behavior, initializes layout/status, starts `loadHashHelper`, and calls `site.js::getSession`. `GetNewSession` updates session/user/output/permission/version state; invalid-session replies to later HTTP and WebSocket requests reacquire a session and retry the request, without rerunning generation-page startup callbacks.
4. On session success, `ListT2IParams` supplies models, wildcards, parameters/groups, and parameter edits. `main.js` composes those through `modelsHelpers`, `buildParameterList`, `paramConfig`, `genInputs`, and `genToolsList`, then invokes `sessionReadyCallbacks` in insertion order and schedules the first history load.
5. A user click, hash restoration, or `openGenPageTabAsync` assigns a top-tab request ID. For a lazy tab, `activateLazyTab` awaits its script group in declared order, calls `GetGenPageTabPartial`, injects the allowlisted/permission-checked Razor partial, enables sliders/translations, and invokes the tab-specific hook. Stale request IDs suppress obsolete continuation and hash work; rejected script/markup work is reset for a later retry.
6. Image Editing's hook initializes its controls/editor; Utilities and User call their lazy initialization/refresh functions; Server initializes server/log helpers and conditionally loads backend types. Server resource and log intervals are gated by tab visibility/document visibility. Extension tabs are eager HTML fragments and extension scripts are classic scripts, not participants in the core lazy-tab manifest.

### Generated output, current image, and history

1. `GenerateHandler.doGenerate` collects parameters through its `getGenInput` facade (base owner `params.js`), preloads the selected model when needed, and opens or reuses `GenerateText2ImageWS` through `makeWSRequestT2I`/`makeWSRequest` (`generatehandler.js`, `generatecontrols.js`, and `site.js`). `internalHandleData` owns request/batch tracking, progress/preview replacement, completion, interrupt cleanup, and socket-intention close handling.
2. Preview messages call the handler/current-image preview path and create or update generating cards without notifying history. A final image either calls `gotImageResult` for a new card or `gotTrackedImageResult` for a tracked card. Those paths update the visible current/batch image through `currentimagehandler.js` and call global `notifyImageHistorySavedPath` when present.
3. `notifyImageHistorySavedPath` delegates to `ImageHistoryController.notifySavedPath`. The controller rejects data/placeholder paths, normalizes the output path, records it in a selected target set, attempts an optimistic insertion against the active folder/depth/filter/sort state, and schedules bounded confirmation refreshes. Current-image explicit save and built-in Grid Generator completion use the same compatibility notification.
4. Independently, `main.js` schedules the history browser's initial navigation after parameter startup, and the History bottom-tab event also calls `scheduleInitialLoad`. `ImageHistoryController.listFolderAndFiles` makes a fast-first root `ListImages` request capped at 128, maps/sorts/filters and renders it, then makes a background request without an explicit client limit. `ImageHistoryAPI` caps both indexed and scan-path returned files at the user's `MaxImagesInHistory` setting (default 1,000), so the background result is the configured returned cap or fewer matching entries rather than the total history. Foreground load tokens and background token/request-key checks discard stale responses; one initial retry, two background retries, and a ten-second watchdog provide bounded recovery/status behavior.
5. A committed full response replaces `GenPageBrowserClass` contents and its `lastFiles`/`lastFilesMap` state. `ImageHistoryFilter` parses metadata through its bounded cache and supplies synchronous matcher/search fields; `ImageHistoryWindowManager` coalesces scroll/resize work and hydrates media near the visible rows. Selecting a history entry delegates back to controller `selectOutput`, which calls `setCurrentImage`; comparison and bulk handlers snapshot controller selection and delegate to their collaborators.
6. Single-image and bulk mutations use `genericRequest`, update controller/browser/card state through callbacks, and request coalesced refreshes. Bulk workflows serialize requests deliberately per selected image except the explicit `BulkMoveImages` route, retain partial-success counts, and release busy state in `finally`. The `imageHistoryBrowser`, `registeredMediaButtons`, and handler globals preserve current-image and extension-facing classic-script compatibility.

## Evidence-Backed Findings

### Frontend F1 — WebSocket invalid-session retry drops caller lifecycle handlers

- **Boundary and exact evidence:** `site.js::makeWSRequest(url, in_data, callback, depth, errorHandle, onOpenHandle)` uses the supplied `errorHandle` for initial failures and calls `onOpenHandle` after the initial socket opens. On an `invalid_session_id` message, lines 130–138 at the pinned base call `getSession` and then `makeWSRequest(url, in_data, callback, depth + 1)` without either handler.
- **Known maintained consumers:** `generatecontrols.js::makeWSRequestT2I` passes generation error handlers; `GenerateHandler.doGenerate` depends on that handler to clear socket/tracked-card state and report/retry previews. `models.js::trt_modal_create`, Utilities' LoRA extraction and model download flows, and `installer.js` also call `makeWSRequest`; the model and Utilities flows pass UI-restoring error handlers. The installer disables `installer_button_confirm` before its request and restores it only in the supplied error handler, so a failed invalid-session retry can leave that button disabled. External classic-script consumers cannot be inventoried and are a preservation constraint.
- **Current control flow:** the first socket preserves caller callbacks. If the server rejects its session, the transport reacquires a session and creates a second socket. Errors on that retry take the generic `showError` path, and its open event cannot invoke the original `onOpenHandle`.
- **Problem/risk and certainty:** a retry after session renewal changes the request's error/open lifecycle contract. For generation this can bypass the handler that clears the tracked socket/cards; for TensorRT or Utilities it can bypass button/progress restoration; for the installer it can leave the confirm button disabled. The argument loss and changed branch are **statically confirmed**; how often invalid-session renewal coincides with a later error is runtime-dependent.
- **Compatibility constraints and existing pattern:** preserve callback timing, depth limit, request mutation/session attachment, streaming message delivery, returned socket behavior, `makeWSRequestT2I`, and extension callers. `genericRequest` already forwards its `errorHandle` and timeout through invalid-session recursion.
- **Bounded opportunity and migration:** first forward `errorHandle` and `onOpenHandle` through only the recursive call; then statically trace every maintained caller and, if desired in a separate project, clarify socket-close ownership without changing it. Rollback is the one transport-call argument change.
- **Verification and validation:** static verification compares both recursion signatures and all maintained consumers and checks syntax only. Maintainer validation should force session invalidation during generation, TensorRT creation, LoRA extraction, model download, and installer submission, then exercise both successful retry and retry failure and confirm cleanup/UI state and streaming remain unchanged. After an installer retry failure, explicitly confirm that `installer_button_confirm` is enabled again.

### Frontend F2 — a session-ready exception aborts later startup owners

- **Boundary and exact evidence:** base `main.js` defines global `sessionReadyCallbacks`, then in the successful `ListT2IParams` callback iterates it with `callback()` and no per-callback error boundary. The statements after the loop start the Krita poll and welcome/title work, set `swarmHasLoaded`, and schedule initial history loading.
- **Known maintained consumers:** `main.js` registers the server-lazy-tab activation check; `promptlab.js` registers `promptLab.init`; `settings_editor.js` registers `loadSettingsEditor`; maintained built-in scripts register `comfyCheckPrep`, permission-gated Grid Generator registration, and Image Batch Tool registration (`ComfyUIBackend/Assets/comfy_workflow_editor_helper.js`, `GridGenerator/Assets/grid_gen.js`, and `ImageBatchTool/Assets/image_batcher.js`). Excluded external extension consumers cannot be enumerated. No `postSessionReadyCallbacks` surface exists at this base.
- **Current control flow:** callbacks run synchronously in insertion order after model/parameter UI construction. An exception escapes the `ListT2IParams` success callback, skips every later callback and the remaining startup tail, and is not converted by `genericRequest` because it occurs in the response callback.
- **Problem/risk and certainty:** one feature initializer can prevent unrelated later initializers and core startup completion/history scheduling. The propagation and skipped statements are **statically confirmed**; no claim is made that a maintained callback currently throws in normal use.
- **Compatibility constraints and existing pattern:** preserve callback order and synchronous invocation for classic-script/extensions, and do not rename/remove the array in the first stage. Nearby lazy-tab/hash promise continuations already catch and display initialization failures while allowing the page to remain usable.
- **Bounded opportunity and migration:** introduce a small dispatcher in `main.js` that invokes each existing callback in order under an individual `try`/`catch`, reports callback position/identity when available, and continues; only afterward consider a registration helper while leaving the array compatible. The rollback boundary is the dispatcher call site.
- **Verification and validation:** static verification enumerates all pushes, proves the tail always executes after a thrown synthetic callback in source-level review, and checks extension script order. Maintainer validation should inject one throwing callback between known callbacks and confirm the error is visible, later callbacks run, `swarmHasLoaded` becomes true, history schedules, and normal startup order is unchanged.

### Frontend F3 — lazy-tab identity is duplicated across three composition owners

- **Boundary and exact evidence:** `Text2Image.cshtml` hard-codes `imageediting`, `utilities`, `user`, and `server` in its Razor `lazyTabs` list and emits separate `genpageLazyScriptGroups`; base `main.js` separately hard-codes those keys in `lazyTabState` and `lazyTabHooks`; `UtilAPI.LazyGenPageTabPartials` independently maps the same keys to partial paths and permissions. `hashSubTabMapping` separately maps three generated tab IDs to sub-tab lists.
- **Known maintained consumers:** Text2Image consumes its Razor list for client descriptors and placeholder panes; `main.js` consumes `window.genpageLazyTabs` in lookup, activation, hash, and server-loop paths and its script manifest in editor/server readiness; `genericRequest('GetGenPageTabPartial')` calls the Util API allowlist; the four partials supply the injected DOM. No extension participates in this core allowlist.
- **Current data/control flow:** a client manifest key selects a hard-coded state/hook, loads a client script group, then sends the key to an independently allowlisted server partial. The current four mappings agree.
- **Problem/risk and certainty:** adding, removing, or renaming a lazy tab requires synchronized edits in Razor, JavaScript state/hooks, and C# allowlisting; a mismatch can yield no state/hook, an invalid-tab response, a wrong permission, or a shell that never initializes. The duplicated mappings are **statically confirmed**; the future omission risk is **strongly inferred**, not a current runtime failure.
- **Compatibility constraints and existing pattern:** preserve public `window.genpageLazyTabs`/`genpageLazyScriptGroups`, tab keys/IDs, partial permissions, Bootstrap/hash behavior, exact script order, and external calls to `openGenPageTab`. The Razor list already demonstrates a single descriptor driving both manifest and shell markup.
- **Bounded opportunity and migration:** first derive generic `lazyTabState` entries from `window.genpageLazyTabs` while retaining explicit hooks; then define server/Razor tab descriptors from one C# source or add a static parity check, continuing to emit the same window manifests. Hash sub-tab mapping can remain explicit because it represents different behavior. Each stage can roll back independently to its literal map.
- **Verification and validation:** static verification compares emitted keys, allowlist keys, partials, permissions, hooks, script groups, and tab IDs and checks unknown/failed-key behavior. Maintainer validation opens every lazy tab by click and hash under allowed/denied permissions, retries a failed asset/partial load, switches tabs rapidly, and verifies extension tabs are unaffected.

### Frontend F4 — generic API error logging includes complete request payloads

- **Boundary and exact evidence:** when an HTTP API response contains `data.error`, `site.js::genericRequest` logs both the server error and ``Input was ${JSON.stringify(in_data)}`` before invoking the caller/default failure path. Maintained `usertab.js::APIKeyHelper.onSaveButton` calls `SetAPIKey` with `{ keyType, key }`; user/admin password flows submit client prehashes, and multiple image/history/generation paths submit metadata or image data through the same transport.
- **Known maintained consumers:** the complete maintained consumer boundary is the one listed in Current Architecture: built-in Comfy and Grid Generator assets; Server Razor; current-image, generation, history, model, note, parameter, preset, wildcard, editor, settings, Prompt Lab, backend/log/server, Simple/User/Utilities, translation, and internal site paths. The sensitive concrete consumer is `usertab.js`; external callers remain a compatibility constraint.
- **Current control flow:** only a server-returned error reaches this payload log. Network/timeout failures use `describeRequestFailure`; callers with an `errorHandle` still receive the error after logging. Because `genericRequest` adds `session_id` to `in_data`, that identifier is also included.
- **Problem/risk and certainty:** a rejected API-key request writes the submitted key and session identifier to the browser console; other rejected requests may write large or private payloads. This disclosure path is **statically confirmed**. Console retention/access and the frequency of server errors are environment-dependent.
- **Compatibility constraints and existing pattern:** preserve endpoint/error context, caller error callbacks, retry behavior, and useful diagnostics. `describeRequestFailure` already reports the endpoint and failure type without serializing input; endpoint-specific UI paths report safe identifiers or aggregate counts.
- **Bounded opportunity and migration:** remove full payload serialization from the shared transport or replace it with a conservative allowlisted/redacted diagnostic summary; do not attempt to infer secret field names from arbitrary extension payloads. Stage the transport change first, then audit any endpoint-specific diagnostics. Rollback is isolated to the diagnostic statement/formatter.
- **Verification and validation:** static verification searches all logging paths and representative sensitive/large callers and confirms errors still reach callbacks/UI. Maintainer validation triggers rejected API-key and ordinary requests and confirms endpoint/error diagnostics remain useful while keys, session IDs, images, and metadata are absent from the console.

## Performance Opportunities and Measurement Requirements

### Client P1 — full image-history response processing and DOM replacement

- **Entry point and frequency:** `ImageHistoryController.listFolderAndFiles` runs on initial navigation, folder navigation, filters, sorts, and refreshes; the fast-first root path immediately schedules `queueFullLoad`, which performs a second full response and `replaceBrowserContents`.
- **Cardinality/configured bound:** fast-first is capped at 128. The background `ListImages` request supplies no explicit general client limit, but `ImageHistoryAPI` caps returned files at the user's `MaxImagesInHistory` setting (default 1,000) on both indexed and scan paths. Its `data.files` length is therefore the configured returned cap or the smaller matching response, not total history cardinality.
- **Execution and existing mitigation:** response processing is synchronous on the browser thread: folder sort, two-pass pre/post ordering, mapping, optional client sort, grid filtering, then `GenPageBrowserClass.build` and `lastFilesMap` construction. The network request is asynchronous. Existing mitigations include fast-first paint, server-side filter text, server-supported sorts, a bounded metadata cache, stale-response tokens, browser list cache, and explicit request/map/render timing logs.
- **Certainty/category:** the repeated linear passes, optional `O(n log n)` client sort, and full replacement are **statically confirmed**. Material user impact is a **plausible material cost requiring measurement**, not a confirmed bottleneck.
- **Required measurement and decision gate:** record existing `History load`/`History background load` request, map, and render fields plus main-thread long tasks for representative small, medium, and largest maintainer histories, each view mode, structured/text filters, client-only sorts, refresh, and folder depth. Separate server time from map/render. Only if client map/render is material should a future design reduce passes, incrementally reconcile results, or bound/virtualize DOM work; it must preserve ordering, selection, optimistic insertion, compatibility accessors, and stale-response behavior.

### Client P2 — visible-history window recomputes layout for every rendered entry

- **Entry point and frequency:** `ImageHistoryWindowManager.attach` binds history-content scroll and window resize; each event is coalesced to one animation frame by `queueUpdate`, and browser builds/tab shows also queue an update.
- **Cardinality/configured bound:** `updateVisibleWindow` converts every content child with `data-name`, reads every entry's `offsetTop`/`offsetHeight` to rebuild rows, scans from both ends for the visible range, then walks every row to hydrate/dehydrate. Work scales with all rendered history entries, up to the configured `MaxImagesInHistory` response cap (default 1,000) or the smaller matching response.
- **Execution and existing mitigation:** this is synchronous main-thread DOM/layout work. Request-animation-frame coalescing prevents duplicate same-frame updates, the row buffer reduces media churn, and off-window image sources are removed. `BrowserMediaWindowManager` provides a similar cached-owner pattern for model browsers, but neither implementation caches row geometry across scroll events.
- **Certainty/category:** the `O(n)` scans and layout reads per queued update are **statically confirmed**; whether they affect scrolling on supported devices is a **plausible material cost requiring measurement**.
- **Required measurement and decision gate:** profile scroll/resize frame time and forced-layout events at increasing rendered entry counts and view widths, with animated/still media and after a full background load. If material, evaluate caching row geometry until build/resize or using a bounded observer/virtualization seam; preserve hydration distance, selected/current card DOM, browser events, and fallback behavior. If measurements remain below the maintainer's responsiveness threshold, reject the change.

### Rejected frontend micro-optimization claims

No finding is retained from JavaScript file size, top-level symbol count, inline-handler count, CSS `!important`/z-index/fixed-position counts, or the existence of JSON/DOM/local-storage operations alone. In particular, replacing the history controller's small literal maps, changing `orderFilesForDisplay` solely to avoid one array pass, or converting classic scripts/modules without measured benefit would be speculative micro-optimization or compatibility-expanding redesign. Those ideas remain rejected unless runtime evidence supplies a material cost and a bounded owner.

# SwarmUI Maintainability Architecture Refresh

## Executive Summary

This refresh finds no justification for a wholesale rewrite. The current architecture has recognizable owners and the first four projects from the prior roadmap are complete: Image Editing has a dedicated UI coordinator, T2I route capabilities are split behind compatible surfaces, image-history behavior is decomposed behind one controller, and Swarm-maintained Comfy class/input contracts are cataloged. Those boundaries should remain closed unless new behavioral evidence appears.

The highest-value remaining work is reliability hardening at existing seams. The generic API/T2I diagnostic disclosure, transactional server-settings persistence, and backend persistence protocol are mitigated in production and maintainer-validated; the browser and Comfy diagnostic mitigations remain implemented awaiting their own maintainer validation. Other confirmed risks include workflow replacement publishing before durable write, cross-backend capability state being collapsed into one mutable global set, generation/accounting cleanup gaps, and several smaller transport, lifecycle, cache, and output-state defects. These are independently bounded; combining them into a process-services, scheduler, frontend-module, or Comfy rewrite would increase regression risk without improving the first fixes.

Unranked security prerequisite `S1`, **redact generic server API/T2I submitted-input diagnostics**, is implemented and maintainer-validated. Rank 3, **align OAuth login cookie transport flags**, and rank 4, **make server-settings changes transactional and persistence observable**, have status **Implemented and maintainer-validated.** Maintainer Reaper176 confirmed rank 3's agreed authentication matrix and rank 4's normal build/launch workflow plus full thirteen-case settings transaction/persistence matrix. Trusted proxy scheme establishment remains separately scoped, raw forwarding headers remain untrusted and out of scope, and no benchmark or performance measurement is claimed. Rank 1's shared browser diagnostic and rank 2's Comfy diagnostic/parser boundary remain implemented awaiting their own maintainer validation. `S1` was discovered during rank-2 exception-flow verification and directly continues the same confidentiality boundary. The roadmap still contains its original 24 bounded production projects followed by eight measurement prerequisites—32 numbered ranks total—because `S1` remains an additional unranked security prerequisite and is not counted among them. Performance work is not authorized until its named operation contributes materially under the representative workload; no benchmark numbers are invented here.

## Current Architecture

### Repository and composition baseline

#### Runtime layers

SwarmUI has three principal maintained runtime layers: a classic-script/Razor browser frontend under `src/Pages`, `src/wwwroot/js`, and `src/wwwroot/css`; the C# application and Web/API host under `src`; and Python execution supplied chiefly by excluded upstream Comfy code, with Swarm-owned nodes confined to `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes` (`AGENTS.md`, `src/Core/Program.cs`, and `src/BuiltinExtensions/ComfyUIBackend/ExtraNodes`). Built-in extensions under `src/BuiltinExtensions` connect these layers without changing the executable composition root.

#### Process lifecycle

`Program.Main` is the process composition and lifecycle root (`src/Core/Program.cs`). After loading settings, it calls `Extensions.PrepExtensions`; that method discovers and instantiates extensions, then invokes `OnFirstInit` and `PopulateMetadata` through separate `RunOnAllExtensions` passes (`src/Core/ExtensionsManager.cs`). Back in `Program.Main`, the ordered phases continue with extension `OnPreInit`, model-list and default-parameter registration, construction of `BackendHandler`, `SessionHandler`, and `WebServer`, `Web.PreInit`, extension `OnInit`, model and backend loading, API registration through `BasicAPIFeatures.Register`, Web-host preparation, extension `OnPreLaunch`, and launch. `Program.Shutdown` invokes `PreShutdownEvent`, cancels `GlobalProgramCancel`, stops the Web host, backends, sessions, proxy, and model handlers, then calls extension `OnShutdown` and shuts down output metadata tracking. Process-wide owners remain publicly reachable through `Program.Backends`, `Sessions`, `T2IModelSets`, `Extensions`, `ServerSettings`, `Web`, and `GlobalProgramCancel`.

The exact-token maintained-C# consumer inventory, bounded to `src/**/*.cs` while excluding `src/Data`, external extensions, downloaded nodes, and build output, found: `Program.Backends` 64 occurrences in 18 files; `Program.Sessions` 58 in 8; `Program.T2IModelSets` 45 in 16; `Program.Extensions` 13 in 3; `Program.ServerSettings` 178 in 42; `Program.Web` 5 in 4; and `Program.GlobalProgramCancel` 91 in 25. These counts identify the breadth of the existing composition surface; they do not characterize those references as defective.

`PrepExtensions` first snapshots host dependency names, reads the maintained public-extension catalog, enumerates built-in and enabled external-extension directories, removes `.delete` directories with per-directory error reporting, discovers already loaded `Extension` subclasses, then builds/loads external projects under extension-specific load contexts. `PrepExtension` catches construction/path-discovery failures per type, and `RunOnAllExtensions` catches every phase exception per extension, so one extension failure is logged and later extensions continue. `OnFirstInit` and `PopulateMetadata` run only after discovery/build has completed. The later `OnPreInit`, `OnInit`, `OnPreLaunch`, and `OnShutdown` passes retain list order; that order, the hook names, and the timing of shared-registry contributions are extension compatibility contracts. Comfy uses `OnPreInit` for parameter/provider/model-refresh contributions, `OnInit` for additional parameters and conditional API registration, `OnPreLaunch` for launch-ready behavior, and `OnShutdown` to detach its dynamic parameter provider; Grid Generator registers parameters/permissions in `OnPreInit` and routes in `OnInit`.

Startup error handling is deliberately mixed by phase. Settings parsing catches readable command-line failures and returns before composition; optional update/git/hardware probes run through `RunCheckedTask` and are given a five-second aggregate startup wait; extension hooks are isolated per extension; model refresh catches per handler; and Web launch retries one known invalid host configuration before rethrowing other failures. `Extensions.PrepExtensions().Wait()`, the startup `Task.WaitAll`, `WebApp.WaitForShutdown`, and several process probes are synchronous composition boundaries rather than request dispatch. After launch, a cancellation-aware ten-second loop persists edited backend configuration, and the one-second utility tick thread invokes the registered tick/slow-tick owners under a loop-level exception boundary.

Shutdown can be entered from assembly unload, process exit, ASP.NET `ApplicationStopping`, `WaitForShutdown` completion, restart/control-timeout paths, CI boot, and permission-gated `AdminAPI.ShutdownServer`, which schedules a delayed direct call. It sets the process exit code after a bounded webhook wait, invokes `PreShutdownEvent`, cancels `GlobalProgramCancel`, stops ASP.NET, backends, sessions, proxy, and each model handler, then invokes extension shutdown, closes output-metadata databases, removes the process temp directory, and flushes logs. Extension shutdown remains per-extension isolated, while the composition-level calls before and after it are sequential. Cancellation is signalled before Web/backend/session disposal so background loops and backend work can observe the token; session removal and interruption use their own per-session cancellation sources. The non-atomic entry guard is retained as Core F10 below; no runtime overlap frequency is inferred.

#### Settings and process persistence

`Settings` is an `AutoConfiguration` tree whose public fields define persisted names and reflection metadata. `Program.LoadSettingsFile` reads FDS, applies legacy key migrations for logging, metadata, autocomplete, role limits, and maintenance, then loads the singleton `Program.ServerSettings`; a missing or malformed file is logged and leaves defaults/current values. At the pinned audit base, early startup re-saved normalized settings unless locked, then applied command-line overrides and runtime log settings. The then-void `SaveSettingsFile` respected `LockSettings`, wrote the entire configuration, and mirrored `Maintenance.AutoPullDevUpdates` into the launcher-consumed `src/bin/always_pull` marker; save failures were logged and not thrown. Core F6 records the later observable implementation.

At the pinned audit base, runtime server edits entered through `AdminAPI.ChangeServerSettings`: reflective field lookup rejected unknown and hidden fields, secret placeholders were ignored, authorization enablement had a lockout guard, accepted values mutated `Program.ServerSettings`, and the route saved before path validation/rebuild and `ReapplySettings`. Installation mutated theme/network/install/language fields, saved once installation completed, reloaded backends, and restarted. Extension enable/disable routes mutated `DisabledExtensions` and saved before a restart applied discovery changes; `ExtensionsManager` also removed no-longer-installed names when managing this list. Backend settings have their own `Backends.fds` lifecycle: `BackendHandler.Load`, the post-launch dirty loop, explicit backend edit routes, shutdown, and `Installation` reload are the maintained persistence/process consumers. Core F6 records both the confirmed base defect and its later corrected implementation; Core F7 separately records model-catalog replacement during a path edit.

#### Web/API composition

`WebServer` owns ASP.NET/Razor composition and request routing (`src/Core/WebServer.cs`). `WebServer.Prep` configures middleware, response compression, static files, WebSockets, Razor Pages, shutdown integration, the `/API/{*Call}` dispatcher, output/view routes, extension files, and audio. `API.APIHandlers` is the route registry; `API.RegisterAPICall` adds either an `APICall` or a reflected delegate; and `API.HandleAsyncRequest` owns HTTP/WebSocket parsing, session resolution, permission enforcement, reflective dispatch, and response/error transport (`src/WebAPI/API.cs` and `src/WebAPI/APICallReflectBuilder.cs`). `BasicAPIFeatures.Register` registers account/session/general routes and composes `T2IAPI`, `ModelsAPI`, `BackendAPI`, `AdminAPI`, `UtilAPI`, and `PromptLabAPI` (`src/WebAPI/BasicAPIFeatures.cs`). Static registration searches found 147 `API.RegisterAPICall` sites across 11 maintained C# files, including built-in Comfy, Grid Generator, and Image Batch Tool contributions.

Before endpoint mapping, `WebServer.Prep` installs origin-observation/dev-forwarding middleware, optional CORS preflight handling, optional exact `Authorization`-header enforcement with configured bypass IPs, compression, exception handling, static files, routing, and WebSockets. It maps Razor Pages without antiforgery, `/API/{*Call}`, `/Output`/`/View`, `/ViewSpecial`, `/ExtensionFile`, and `/Audio`, then installs a terminal 404 redirect. Output/audio/special routes resolve a user separately through `WebServer.GetUserFor`/`WebUtil.GetValidLogin`, validate roots with `CheckFilePath`, enforce other-user/model restrictions, and use structured JSON refusal responses. They do not pass through `API.HandleAsyncRequest`.

The API registry key is the lowercase reflected method name, and `Dictionary.Add` makes duplicate route names a fail-fast registration error. Built-in extension `OnInit` registration occurs before `BasicAPIFeatures.Register`: Grid Generator contributes six routes and Image Batch Tool one; Comfy conditionally calls `ComfyUIWebAPI.Register` from its `OnInit` and contributes twelve. Core general/account routes register first inside `BasicAPIFeatures`, followed in fixed order by the T2I, model, backend, admin, utility, and Prompt Lab groups. `T2IAPI.Register` remains the ordered facade for generation, history, Krita, classic-inpaint, parameter-list, and refresh routes. External extensions may register in the same `OnInit` phase, so method names, signatures, registration ordering relative to core, permission objects, and duplicate-name failure behavior are compatibility constraints.

`APICallReflectBuilder` accepts only `Task<JObject>` methods. `HttpContext`, `Session`, `WebSocket`, and a root `JObject` are injected; the root object is copied with `session_id` removed. Primitive and `string[]` arguments bind by exact C# parameter name, use the reflected default when absent, and otherwise return an `error` object on failed coercion. `IDataHolder` parameters accept either a nested object under the parameter name or the root object, apply field names/required metadata, and support only registered coercer types. A `WebSocket` parameter marks the whole route as WebSocket-only. Consequently route method names, parameter names/types/defaults, `IDataHolder` field names, API attributes, and whether a socket parameter exists are wire/reflection contracts.

`API.HandleAsyncRequest` accepts one bounded WebSocket JSON message or a non-empty bounded JSON POST; other HTTP methods redirect to `NoGetAPI`. Except for the explicit lowercase sessionless set (`login`, `getnewsession`, `registerbasic`, `registeroauth`, and `getactivekritasession`), it resolves `session_id` from JSON or `X-Session-ID`, rehydrates persisted sessions through `SessionHandler.TryGetSession`, ticks user presence/update time, then checks the registered permission before binding. Unknown routes, transport mismatch, missing/invalid sessions, and permission failures have structured IDs, but HTTP and WebSocket status/close paths differ. Handler-returned `error` objects are logged and still transported as normal handler output (HTTP 200); thrown exceptions are logged with detail and converted to generic `internal_error`. `RunWebsocketHandlerCallWS` drains queued stream frames but currently logs a fault without sending a failure frame, which is Core F5. Frontend F4 records the pinned-base client-side full-input disclosure; its mitigation is implemented and awaiting maintainer validation. Server dispatch does not log the complete request object on ordinary handler errors, though parser exceptions, reflective validation/error messages, and route-specific logs can include submitted values as separately bounded below.

On the browser side, `ImageHistoryController` remains in `src/wwwroot/js/genpage/gentab/outputhistory.js` and composes `ImageHistoryFilter`, `ImageHistoryComparison`, and `ImageHistoryBulkActions` from `src/wwwroot/js/genpage/gentab/imagehistoryfilter.js`, `src/wwwroot/js/genpage/gentab/imagehistorycomparison.js`, and `src/wwwroot/js/genpage/gentab/imagehistorybulkactions.js`; the Image Editing coordinator is owned by `src/wwwroot/js/genpage/helpers/image_editor_ui.js`. These are current committed boundaries, not assumptions carried forward from the 2026-07-20 audit.

#### Extension composition

`ExtensionsManager` discovers built-in extension types from loaded assemblies and external extension projects from `src/Extensions` and instantiates `Extension` subclasses (`src/Core/ExtensionsManager.cs`). Its `RunOnAllExtensions` performs the per-phase iteration requested by callers; `Program` establishes the lifecycle phase order. The `Extension` base contributes `ScriptFiles`, `StyleSheetFiles`, `OtherAssets`, metadata, and `OnFirstInit`/`OnPreInit`/`OnInit`/`OnPreLaunch`/`OnShutdown` hooks (`src/Core/Extension.cs`). Extensions also contribute through shared registries such as `API.RegisterAPICall`, `T2IParamTypes.Register`, `BackendHandler.RegisterBackendType`, permissions, and `WorkflowGenerator` step lists. `WebServer.GatherExtensionPageAdditions` converts extension script/style/asset lists and `Tabs/Text2Image/*.html` files into served resources and generated page fragments. Thus `Program` owns lifecycle order, `ExtensionsManager` owns discovery, instances, and per-phase iteration, each `Extension` owns its contribution declarations, and `WebServer` materializes browser-facing contributions.

#### Backend/session/model state

Backend ownership is centered on `BackendHandler`: `AllBackends` is a concurrent configured-instance registry, `BackendTypes` is the type catalog, `Load` and `Shutdown` own configured lifecycle, and `GetNextT2IBackend` plus request/pressure registries coordinate T2I acquisition and model-loading pressure (`src/Backends/BackendHandler.cs`). `SessionHandler` owns concurrent session, user, and role registries plus persistent login sessions (`src/Accounts/SessionHandler.cs`). Each `T2IModelHandler` owns a concurrent model catalog and refresh/shutdown behavior, while `Program.T2IModelSets` maps model categories to those handlers (`src/Text2Image/T2IModelHandler.cs` and `src/Core/Program.cs`).

`SessionHandler` opens `Users.ldb`, prepares weekly bounded backups, exposes LiteDB collections for users, API sessions, login tokens, presets, generic data, and OAuth lookup, and loads `Roles.fds` under a single `DBLock`. Default roles are synthesized, new permission IDs registered by core/extensions are propagated according to their declared defaults, and the owner wildcard remains authoritative. `API.HandleAsyncRequest` checks the session's stacked `Role` immediately before invocation; parameter-level permissions are checked later by `T2IParamTypes.ApplyParameter`. API sessions are secure-random IDs held in concurrent process/user maps and optionally persisted; rehydration verifies that an originating login token still exists. `Session.GenClaim` tracks queue/live counters with interlocked updates and combines the session interrupt with a local claim interrupt. `Session.Interrupt` cancels the current token source and installs a new one for later work. Persistent browser login tokens are hashed in LiteDB and validated from the HttpOnly cookie by `WebUtil`; revocation removes the login record and associated API sessions. The unbounded pending OAuth challenge map is Core F8; Core F9 records the implemented and maintainer-validated alignment of the historical OAuth cookie flag difference.

`Program.BuildModelLists` derives seven core handler categories from configured roots/subfolders and exposes them through the public `Program.T2IModelSets` dictionary. Each handler subscribes to `Program.ModelRefreshEvent`; `Refresh` validates roots, recursively scans directories in parallel, builds a new concurrent model map, loads cached or embedded/sidecar metadata, then replaces that handler's map under `ModificationLock`. Model names are filtered by the session's role at list/option time. Metadata is cached in LiteDB either centrally or per folder; record reuse is gated by the model file's last-write timestamp, while recomputation inspects safe-tensor/GGUF headers, preview candidates, and up to four sidecar suffixes. Some `ModelsAPI` operations use `Program.RefreshLock` read claims and its download path takes a later write claim; `T2IAPI.TriggerRefresh` uses a write claim, a semaphore, and a ten-second redundancy window. `AdminAPI.ChangeServerSettings` rebuilds the outer model-set dictionary without that lock, as detailed in Core F7. The absence of sidecar freshness from the cache key is Core F12; duplicate sidecar I/O/parsing when recomputation does occur is the separate measurement-gated Core P4.

#### Parameter registry and request conversion

`T2IParamTypes.Types` is the public process-wide parameter registry keyed by cleaned ID. `Register<T>` fixes the ID, wire data type, and `SharpType`, fails on duplicate identity through `Dictionary.Add`, appends language strings, and returns the public typed `T2IRegisteredParam<T>` handle stored in core/extension fields. `RegisterDefaults` owns core groups and default parameters; built-ins add their own parameters during `OnPreInit`/`OnInit`. `ParameterRemaps` preserves four retired IDs, `FakeTypeProviders` allows context-sensitive extension parameters (Comfy supplies the maintained provider), and public fields/groups/list identities are source and mutable-object compatibility surfaces rather than candidates for bulk encapsulation.

`T2IParamType.ToNet` emits the browser contract, including ID/name/type/subtype/default/range/options/display/group/retention fields, and evaluates session-specific option providers. `ListT2IParams` permission-filters types, collects reachable groups, serializes model classes/model lists, and returns parameter edits and remaps. `FromNet` supports remote reconstruction but does not round-trip every server-only delegate/permission field. Option validation uses cleaned exact/best matches, numeric bounds, booleans, lists, and model names restricted through `ListModelNamesFor(session)`. File-backed media references are root-checked, special-history paths are resolved, then the pending-save cache or filesystem is converted to a data URL; Core P3 records that synchronous critical-path mechanism.

`T2IAPI.RequestToParams` creates a session-bound `T2IParamInput`, orders `AlwaysTopKeys` first for extension routing needs, copies `extra_metadata`, ignores transport/preset keys, warns and skips unknown keys, converts arrays to the list separator, and calls `T2IParamTypes.ApplyParameter`/`ValidateParam` for validation, permission checks, parsing, model resolution, and required-feature accumulation. Selected presets are then applied or retained for Grid Generator. Its five maintained caller contexts are core `T2IAPI` generation, `ImageHistoryAPI.AddImageToHistory`, `ComfyUIWebAPI.ComfyGetGeneratedWorkflow`, Grid Generator `GridGenRun`, and Image Batch `GenBatchRun_Internal`. `T2IParamInput` owns the typed set, section overrides, extra metadata, feature/refusal state, pending presets, session interrupt token, unique request ID/time, and queried-parameter tracking. Early handlers normalize resolution/LoRA lists and early preset model selection; late handling parses prompt-like syntax. On the normal engine path, that late pass runs on its task input before backend acquisition; conditional `<preset>`/`<param>` tags can re-enter parameter validation and file-backed media conversion. Comfy workflow preview and `TestPromptFill` also invoke the late pass once. Clones duplicate mutable sets/lists but retain session/cancellation and referenced model/media values. Metadata and reusable API JSON are derived from the same typed set while respecting hide/save/unused contracts.

### Frontend, Razor, and Web composition

#### Layout and classic-script order

`src/Pages/Shared/_Layout.cshtml` is the browser composition root. In the head it emits, in order, the selected dark/light Bootstrap stylesheet, Select2 styles, `site.css`, the page `Header` section, extension styles through `WebServer.PageHeaderExtra`, and the selected theme styles. It then loads jQuery, Bootstrap, Select2, `util.js`, and `translator.js`. After the page body it loads `permissions.js`, then `site.js`, then the page `Scripts` section. Consequently generation-page code can rely on utility, translation, permission, request, and session globals, while theme CSS has later cascade position than core, page, and extension CSS. This ordering is a compatibility contract; the maintained CSS searches found responsive rules, fixed-position overlays, z-index layers, and `!important` overrides, but those constructs are contextual evidence of the existing cross-theme/browser contract rather than findings.

`src/Pages/Text2Image.cshtml` supplies the generation-page order inside that `Scripts` section. After the excluded EXIF dependency, the base sequence is `welcomemessages.js`, `browsers.js`, presets, wildcards, base `loras.js`, models, params, prompt tools, utility/user-tab definitions, `generatehandler.js`, Simple tab, layout, metadata, generation controls, current-image handling, the three image-history collaborators, `outputhistory.js`, notes, base `main.js`, Prompt Lab, settings editor, UI improvements, and media controls. `WebServer.PageFooterExtra` then appends extension scripts; `finalscript.js` is last and schedules `genpageLoad` with a one-millisecond timeout. Static source establishes declaration and scheduling order, not when a particular browser will execute the queued timer relative to unrelated work.

`Extension.ScriptFiles`, `StyleSheetFiles`, and `OtherAssets` are public contribution lists populated by extensions (`src/Core/Extension.cs`). `WebServer.GatherExtensionPageAdditions` iterates `Program.Extensions.RunOnAllExtensions`: scripts and styles become cache-varied `ExtensionFile/{ExtensionName}/...` tags, other assets become served binary entries, and `Tabs/Text2Image/*.html` files become permission-gated top-tab header/body fragments. It assigns the resulting strings to `PageFooterExtra`, `PageHeaderExtra`, `T2ITabHeader`, and `T2ITabBody` (`src/Core/WebServer.cs`). Text2Image places extension tab headers between Image Editing and Utilities, extension bodies after the Image Editing shell, and extension scripts immediately before `finalscript.js`. Extension order, classic-script globals, tab IDs, and the final-script position must therefore remain compatible even though external extensions are outside the auditable consumer inventory.

#### Generation-page initialization, session callbacks, and lazy tabs

`genpageLoad` in base `src/wwwroot/js/genpage/main.js` first binds Bootstrap top-tab handlers, initializes `genTabLayout`, starts a status request, and starts hash restoration. It then calls `getSession` from `site.js`. A successful `GetNewSession` sets `session_id`, `user_id`, output-prefix behavior, permissions, and server-version state before invoking the callback. ### Frontend F1 — WebSocket invalid-session retry drops caller lifecycle handlers

- **Boundary and exact evidence:** `site.js::makeWSRequest(url, in_data, callback, depth, errorHandle, onOpenHandle)` uses the supplied `errorHandle` for initial failures and calls `onOpenHandle` after the initial socket opens. On an `invalid_session_id` message, lines 130–138 at the pinned base call `getSession` and then `makeWSRequest(url, in_data, callback, depth + 1)` without either handler. The only maintained `onOpenHandle` consumer is `ModelDownloaderUtil.download` in `utiltab.js`: it binds the cancel button to send a cancel signal through the opened socket and then enables that button.
- **Known maintained consumers:** `generatecontrols.js::makeWSRequestT2I` passes generation error handlers; `GenerateHandler.doGenerate` depends on that handler to clear socket/tracked-card state and report/retry previews. `models.js::trt_modal_create`, Utilities' LoRA extraction and model download flows, and `installer.js` also call `makeWSRequest`; the model and Utilities flows pass UI-restoring error handlers. External classic-script consumers cannot be inventoried and are a preservation constraint.

The argument loss and changed branch are **statically confirmed**; how often an invalid session reaches either a successful retry needing cancellation or a later retry error is runtime-dependent.
- **Compatibility constraints and existing pattern:** preserve callback timing, depth limit, request mutation/session attachment, streaming message delivery, returned socket behavior, `makeWSRequestT2I`, and extension callers. `genericRequest` already forwards its `errorHandle` and timeout through invalid-session recursion.
- **Bounded opportunity and migration:** first forward `errorHandle` and `onOpenHandle` through only the recursive call; then statically trace every maintained caller and, if desired in a separate project, clarify socket-close ownership without changing it. Rollback is the one transport-call argument change.
- **Verification and validation:** static verification compares both recursion signatures and all maintained consumers and checks syntax only. Maintainer validation should force session invalidation during generation, TensorRT creation, LoRA extraction, model download, and installer submission, then exercise both successful retry and retry failure and confirm cleanup/UI state and streaming remain unchanged. ## Performance Opportunities and Measurement Requirements

All eight retained candidates are classified **Plausible material cost requiring measurement before change**. Their repeated work is structurally confirmed, but its materiality is not. No candidate currently qualifies as **Confirmed structural waste suitable for behavior-preserving removal** because each algorithm change still needs workload evidence, and the explicitly dismissed file-size/count/style claims are **Rejected speculative micro-optimization**. Measurements authorize a later design only when the named cost contributes materially to the stated latency, CPU, allocation, memory, lock, or frame-time boundary; they never authorize a behavior change directly.

### Client P1 — full image-history response processing and DOM replacement

- **Entry point and frequency:** `ImageHistoryController.listFolderAndFiles` runs on initial navigation, folder navigation, filters, sorts, and refreshes; the fast-first root path immediately schedules `queueFullLoad`, which performs a second full response and `replaceBrowserContents`.
- **Cardinality/configured bound:** fast-first is capped at 128. The background `ListImages` request supplies no explicit general client limit, but `ImageHistoryAPI` caps returned files at the user's `MaxImagesInHistory` setting (default 1,000) on both indexed and scan paths. Its `data.files` length is therefore the configured returned cap or the smaller matching response, not total history cardinality.
- **Execution and existing mitigation:** response processing is synchronous on the browser thread: folder sort, two-pass pre/post ordering, mapping, optional client sort, grid filtering, then `GenPageBrowserClass.build` and `lastFilesMap` construction. The network request is asynchronous. Existing mitigations include fast-first paint, server-side filter text, server-supported sorts, a bounded metadata cache, stale-response tokens, browser list cache, and explicit request/map/render timing logs.
- **Certainty/category:** the repeated linear passes, optional `O(n log n)` client sort, and full replacement are **statically confirmed**. Material user impact is a **plausible material cost requiring measurement**, not a confirmed bottleneck.
- **Required measurement and decision gate:** record existing `History load`/`History background load` request, map, and render fields plus main-thread long tasks for representative small, medium, and largest maintainer histories, each view mode, structured/text filters, client-only sorts, refresh, and folder depth. Separate server time from map/render. Only if client map/render is material should a future design reduce passes, incrementally reconcile results, or bound/virtualize DOM work; it must preserve ordering, selection, optimistic insertion, compatibility accessors, and stale-response behavior.

### Client P2 — visible-history window recomputes layout for every rendered entry

- **Entry point and frequency:** `ImageHistoryWindowManager.attach` binds history-content scroll and window resize; each event is coalesced to one animation frame by `queueUpdate`, and browser builds/tab shows also queue an update.
- **Cardinality/configured bound:** `updateVisibleWindow` converts every content child with `data-name`, reads every entry's `offsetTop`/`offsetHeight` to rebuild rows, scans from both ends for the visible range, then walks every row to hydrate/dehydrate. Work scales with all rendered history entries, up to the configured `MaxImagesInHistory` response cap (default 1,000) or the smaller matching response.
- **Execution and existing mitigation:** this is synchronous main-thread DOM/layout work. Request-animation-frame coalescing prevents duplicate same-frame updates, the row buffer reduces media churn, and off-window image sources are removed. `BrowserMediaWindowManager` provides a similar cached-owner pattern for model browsers, but neither implementation caches row geometry across scroll events.
- **Certainty/category:** the `O(n)` scans and layout reads per queued update are **statically confirmed**; whether they affect scrolling on supported devices is a **plausible material cost requiring measurement**.
- **Required measurement and decision gate:** profile scroll/resize frame time and forced-layout events at increasing rendered entry counts and view widths, with animated/still media and after a full background load. If material, evaluate caching row geometry until build/resize or using a bounded observer/virtualization seam; preserve hydration distance, selected/current card DOM, browser events, and fallback behavior. If measurements remain below the maintainer's responsiveness threshold, reject the change.

### Core P4 — model sidecars are read and parsed twice during metadata-cache recomputation

- **Entry point and frequency:** `T2IModelHandler.Refresh` recursively scans model folders and calls `AddAllFromFolder`, which calls `LoadMetadata` for discovered models. Folder recursion and model discovery run in parallel. - **Certainty/category:** duplicate sidecar I/O and parsing in the same recomputation branch are **statically confirmed**. Aggregate user impact depends on recomputed model count, sidecar prevalence/size, and filesystem latency; materiality is unknown.
- **Required measurement and decision gate:** time missing-record, reusable-record, changed-model-mtime, and legacy-`TextEncoders` refresh cases while recording model count, recomputed count, existing suffix count/bytes, storage type, sidecar read/parse time, and total refresh/event latency. Defer a maintainability-only duplicate-pass cleanup and reject broader scan/cache redesign without supporting measurements. This optimization does not address Core F12's cache-freshness contract.
